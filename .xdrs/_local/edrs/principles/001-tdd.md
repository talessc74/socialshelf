# _local-edr-policy-001: TDD Obrigatória

## Context and Problem Statement

Código sem testes prévios tende a ser difícil de testar depois — porque o design foi feito sem testabilidade como restrição. Em um sistema com integrações externas (OAuth, Vertex AI, Firestore), a separação entre lógica testável e infraestrutura não testável é uma decisão de design, não uma propriedade emergente.

Como garantir que toda funcionalidade seja testável nativamente e que testes existam antes da implementação?

## Decision Outcome

**Red-Green-Refactor: toda feature começa com o teste que falha**

Testabilidade nativa é requisito de design. Código que não pode ser testado sem infraestrutura real representa falha de design arquitetural, não limitação de ferramenta.

### Details

**Ciclo obrigatório**

1. **Red**: Escreva o teste que falha. O teste descreve o comportamento esperado, não a implementação.
2. **Green**: Implemente o mínimo necessário para o teste passar.
3. **Refactor**: Melhore o código sem quebrar o teste.

**Ferramentas**

- Vitest em todos os apps backend (`api`, `publisher`, `generator`).
- Vitest ou Jest (via Next.js) para lógica de frontend testável em isolamento.
- Coverage mínima rastreada em CI (`pnpm test:coverage` com upload de artefatos).

**Testabilidade como critério de design**

- Use-cases devem ser testáveis com mocks dos ports — sem Firestore, sem Secret Manager, sem chamadas HTTP externas.
- Adapters de infraestrutura (`FirestoreOAuthRepository`, `XPublisher`) são testados em isolamento com mocks do SDK correspondente.
- Se um use-case não pode ser testado sem infraestrutura real, o design de dependências está errado — refatore antes de implementar.

**O que não justifica ausência de testes**

- Pressão de prazo
- "É só um script"
- "Vou adicionar os testes depois"
- "É código de infraestrutura"

**Dívida de teste**

Funcionalidade sem teste não é funcionalidade entregue. Refatoração de código sem teste deve começar criando o teste que cobre o comportamento atual antes de qualquer mudança.
